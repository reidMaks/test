# Аналіз та план вирішення проблеми: Disaster Recovery (Home Offline)

Цей документ описує поточний стан кластера у сценарії, коли домашня мережа повністю офлайн (наприклад, зникло світло), а також кроки, необхідні для забезпечення повноцінного доступу до сервісів (High Availability).

## 🚨 Поточна проблема

Незважаючи на те, що OCI-нода та GCP-нода продовжують працювати і зберігають кворум (кластер Kubernetes функціонує, поди перенесені та запущені), **доступ до кластера ззовні неможливий** з трьох причин:

1. **Заблокований доступ до API (Фаєрвол OCI)**
   В конфігурації Oracle Cloud (`oci.tf`) налаштовано жорсткий фаєрвол (Security List). Відкриті лише порти `50000` (Talos API) та `51820` (WireGuard KubeSpan). Порти доступу до Kubernetes API (`6443`) та веб-трафіку (`80`, `443`) закриті для зовнішнього світу.

2. **Локальний Kubeconfig**
   Згенерований файл `kubeconfig` налаштований на підключення до домашнього IP `192.168.0.40`. Коли домашня мережа недоступна, `kubectl` не може знайти цей IP і просто зависає/видає помилку.

3. **Маршрутизація трафіку (MetalLB + DNS)**
   Домени (наприклад, `*.kms-lab.in.ua`) зараз вказують на IP `192.168.0.45`. Це внутрішня адреса, яку видає балансувальник MetalLB у домашній Layer-2 мережі. Навіть якщо Traefik запуститься на OCI-ноді, зовнішній трафік фізично туди не дійде, оскільки DNS відправляє його на вимкнений домашній роутер.

## 🛠 Детальний план вирішення (Solution Details)

Щоб кластер став повністю автономним і публічно доступним у разі "падіння" домашнього сервера, необхідно реалізувати наступні архітектурні зміни:

### Крок 1: Оновлення фаєрвола OCI (Security Lists)
Необхідно внести зміни до файлу `infra/oci.tf`, щоб дозволити вхідний трафік (Ingress) на порти, критичні для зовнішнього доступу:
- **`6443/TCP`**: Для підключення `kubectl` напряму до OCI-ноди.
- **`80/TCP`, `443/TCP`**: Для вхідного HTTP/HTTPS трафіку до ваших додатків.

### Крок 2: Адаптація Kubeconfig
Щоб мати можливість адмініструвати кластер у будь-який момент, потрібно додати OCI-ноду як резервну точку входу в Kubernetes API:
- Можна змінити кластерний endpoint на публічний IP OCI.
- Або додати кілька контекстів у `kubeconfig` (один для `home`, один для `oci_fallback`). Оскільки `certSANs` на OCI-ноді вже містить її публічний IP, сертифікати співпадуть і підключення пройде успішно.

### Крок 3: Налаштування Ingress для OCI
MetalLB не може анонсувати публічні IP-адреси Oracle Cloud, оскільки він працює лише в локальній BGP/ARP мережі. Щоб Traefik міг приймати трафік на OCI-ноді, є кілька варіантів:
- **Варіант А (Простий):** Налаштувати Traefik (або його копію/DaemonSet) на використання `hostPort` або `hostNetwork: true`. Тоді Traefik прив'яжеться безпосередньо до портів `80/443` публічного інтерфейсу OCI-ноди.
- **Варіант Б (Oracle LB):** Розгорнути безкоштовний (у рамках Free Tier) Oracle Cloud Load Balancer, який буде перенаправляти трафік на NodePort Traefik-а. Це класичний Cloud-Native підхід, але він вимагає додаткового Terraform-коду.

### Крок 4: Глобальна маршрутизація (DNS Failover)
Трафік має автоматично перемикатися на OCI, якщо домашній MetalLB недоступний. Це вирішується на рівні DNS:
- Якщо ви використовуєте **Cloudflare**, можна налаштувати Cloudflare Load Balancing (може бути платним) або просто додати другий A-запис (Round-Robin DNS), хоча це дає затримку у клієнтів.
- **Оптимально (Cloudflare Tunnels):** Замість відкриття портів на OCI, можна запустити `cloudflared` (Cloudflare Tunnel) прямо в кластері. Тоді кластер сам пробиває захищений тунель до Cloudflare (працює і з дому, і з OCI). Де б не запустився под тунелю (вдома чи на OCI), Cloudflare завжди знайде його і переправить трафік. Це вирішує проблему MetalLB і Фаєрволів одним махом!

### Рекомендація
Найсучаснішим і найбезпечнішим підходом для мульти-хмарних кластерів (як ваш) є використання **Cloudflare Tunnels**. Це дозволить не відкривати порти 80/443 взагалі і забезпечить моментальне перемикання трафіку (HA), незалежно від того, на якій ноді зараз фізично знаходяться ваші сервіси.
