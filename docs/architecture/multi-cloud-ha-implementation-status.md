# Multi-Cloud HA Cluster: Актуальний стан впровадження

Цей документ описує поточний статус реалізації архітектури, описаної в [multi-cloud-ha-cluster.md](./multi-cloud-ha-cluster.md).

## ✅ Завершені етапи (Виконано)

1. **Єдина монолітна IaaC-інфраструктура:**
   - Старі розрізнені конфігурації (`infra-gcp`, `infra-oci`) успішно перенесені та інтегровані в єдиний стейт в каталозі `infra/`. 
   - Тепер весь життєвий цикл гібридного кластера (Proxmox + GCP + OCI) управляється однією командою `terraform apply`.

2. **GCP Tiebreaker Node (Witness):**
   - Успішно розгорнуто інстанс `e2-micro`.
   - Нода працює виключно як Control Plane для підтримки кворуму `etcd`.
   - Автоматично приєдналася до KubeSpan.

3. **Oracle Cloud Node (CP + Worker на ARM64):**
   - Успішно розв'язано проблему несумісності кастомних образів з ARM-процесорами в OCI. 
   - Налаштовано **повністю автоматизований пайплайн імпорту**: завантаження RAW-образу від Sidero, конвертація в `qcow2`, генерація `image_metadata.json` (з прив'язкою до `VM.Standard.A1.Flex` та `UEFI_64`), пакування в формат `.oci` та заливка в публічний бакет (Object Storage) для імпорту.
   - Знято блокування `NoSchedule` (`allowSchedulingOnControlPlanes: true`), що робить 4-ядерний ARM-сервер повноцінним воркером.
   - Явно додано лейбл `node-role.kubernetes.io/control-plane: ""` для збереження логічної ролі в `kubectl`.

4. **KubeSpan (WireGuard Mesh):**
   - Успішно створено захищену мережу. Всі вузли, незалежно від їх фізичного розташування (Домашній роутер, Швейцарія, США), об'єднані в єдиний L2/L3 простір.
   - Кластер має надійний кворум із 3-х нод (Home, GCP, OCI). Відключення будь-якої однієї локації не призведе до падіння кластера.

## 🛠 Технічні нюанси та відхилення від плану

- **Ручне схвалення CSR:** Під час ініціалізації OCI-ноди, вбудований контролер Talos не встиг автоматично схвалити Certificate Signing Request для Kubelet (ймовірно, через затримку синхронізації `etcd` або зміну архітектури). Потребувало разового ручного `kubectl certificate approve`. Сертифікати видані, ротація відбуватиметься автоматично.
- **Діагностичний доступ (certSANs):** Для прямого доступу до OCI-ноди через її публічну IP-адресу в обхід KubeSpan (для читання логів), у `talos.tf` було додано її публічний IP в `certSANs`.

## ⏳ Наступні кроки (До виконання)

1. **Storage Strategy (Longhorn):**
   - Налаштувати збереження резервних копій Longhorn у S3-бакет (Oracle Object Storage або Cloudflare R2), замість єдиної точки відмови (локальний NAS).
   - Переконатися, що репліки Longhorn розгортаються виключно на домашніх нодах (щоб уникнути високих WAN-затримок при синхронному записі між Україною та Швейцарією).

2. **Очищення репозиторію:**
   - Виконати `terraform destroy` у старих каталогах `infra-oci` та `infra-gcp`.
   - Видалити ці каталоги з системи та зробити Git Commit з чистою інфраструктурою.

3. **Маршрутизація трафіку (Cloudflare Tunnels):**
   - Підтвердити, що поди `cloudflared` успішно розгортаються і балансують трафік, навіть якщо частина 워рклоадів переїде на потужну ноду Oracle.
