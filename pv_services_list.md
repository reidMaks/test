# Список сервісів з Persistent Volumes (PV) та план відмови від георозподіленої реплікації Longhorn

Нижче наведено перелік усіх сервісів у кластері, які використовують персистентні томи (Persistent Volume Claims), разом з їхніми базами даних, призначенням дисків, а також планом міграції для відключення реплікації Longhorn на OCI (щоб сервіси залишались працездатними у хмарі при відключенні дому).

## 1. Actual Budget (`actualbudget`)
- **База даних:** Вбудована SQLite.
- **Навіщо диск:** Зберігання файлів внутрішньої бази даних та користувацької інформації про бюджети (монтується у `/data`).
- **Готовність до відключення реплікації:** Ні
- **План робіт:**
  - Налаштувати **Litestream** для реплікації локальної SQLite-бази в OCI Object Storage.
  - У разі падіння дому OCI-нода зможе відновити стан з бакета (S3) за допомогою Litestream.
  - Інші файли в директорії (наприклад, бекапи, які створює сама програма) можна періодично синхронізувати через rclone або просто ігнорувати, покладаючись на Litestream для консистентності.

## 2. CloudNativePG (`cnpg`)
- **База даних:** Безпосередньо сам кластер бази даних PostgreSQL (`shared-db`).
- **Навіщо диск:** Збереження файлів бази даних PostgreSQL, таблиць, WAL логів (використовує клас `longhorn-postgres`).
- **Готовність до відключення реплікації:** Так (в процесі/готово згідно з архітектурою)
- **План робіт:**
  - Реплікація на рівні дисків Longhorn має бути повністю вимкнена для цих томів, а томи прив'язані виключно до локальних `amd64` нод (`nodeAffinity`).
  - Висока доступність (HA) на OCI вже забезпечується засобами самої PostgreSQL (асинхронна потокова реплікація на OCI arm64-ноду).

## 3. ESPHome (`esphome`)
- **База даних:** Не використовує базу даних.
- **Навіщо диск:**
  - `/config`: Зберігання конфігураційних YAML файлів пристроїв.
  - `/config/.esphome`: Зберігання кешу для пришвидшення компіляції прошивок розумного дому.
- **Готовність до відключення реплікації:** Так
- **План робіт:**
  - Відключити реплікацію PV на OCI. Оскільки сервіс компілює прошивки для пристроїв домашньої мережі, за відсутності доступу до дому він на OCI не має сенсу.
  - Альтернативно: YAML-конфігурації можна зберігати у Git, щоб взагалі відмовитись від PV, а кеш зберігати у тимчасовому `emptyDir`.

## 4. FreeLingo (`freelingo`)
- **База даних:** Спільна PostgreSQL (через CloudNativePG) та власний Redis (для кешу/брокера).
- **Навіщо диск:**
  - Бекенд (`backend`): Збереження згенерованих аватарів (`/app/avatars`) та аудіофайлів (`/data/audio`).
  - Redis (`redis`): Персистентне зберігання даних кешу (`/data`).
- **Готовність до відключення реплікації:** Ні
- **План робіт:**
  - **БД:** PostgreSQL вже реплікується через CNPG.
  - **Redis:** Можна перевести PV на `emptyDir` (Redis тут діє переважно як Celery broker/кеш), пожертвувавши персистентністю при перезапусках.
  - **Файли:** Оскільки ми не вносимо зміни в код сервісів, для зберігання аудіофайлів та аватарів необхідно змонтувати бакет OCI Object Storage як звичайну файлову систему (наприклад, використовуючи S3 CSI драйвер типу rclone mount, JuiceFS або s3fs). Для бекенду це виглядатиме як звичайний диск.

## 5. LubeLogger (`lubelogger`)
- **База даних:** Вбудована SQLite (АЛЕ підтримує PostgreSQL).
- **Навіщо диск:**
  - `/App/data`: Збереження бази даних та фотографій чеків/деталей.
  - `/root/.aspnet/DataProtection-Keys`: Збереження ключів сесій ASP.NET.
- **Готовність до відключення реплікації:** Ні
- **План робіт:**
  - **База даних:** Оскільки LubeLogger підтримує PostgreSQL, ми повністю мігруємо його базу даних на наш спільний кластер **CloudNativePG** (`shared-db`). Це автоматично вирішує проблему реплікації бази даних на OCI без необхідності використання Litestream.
  - **Фотографії:** Використати S3 CSI (rclone mount, JuiceFS) для монтування папки з фото безпосередньо у контейнер. Сервіс буде писати/читати файли з бакета так, ніби це локальний диск.
  - **Ключі ASP.NET:** Перенести зберігання ключів у Kubernetes Secrets або у БД замість диску.

## 6. Paperless-ngx (`paperless`)
- **База даних:** Спільна PostgreSQL (через CloudNativePG) та локальний Redis.
- **Навіщо диск:** Папки `data`, `media`, `consume`, `export`.
- **Готовність до відключення реплікації:** Ні
- **План робіт:**
  - База даних PostgreSQL вже вирішена (CNPG).
  - Paperless-ngx підтримує зберігання документів у S3 (через `django-storages`). Необхідно налаштувати змінні середовища `PAPERLESS_DEFAULT_FILE_STORAGE` для зберігання `media` в OCI Object Storage.
  - Для `data` (індекси, sqlite для якихось локальних кешів) та черг `consume/export` можна залишити прив'язаний до дому локальний диск (або `emptyDir`), оскільки основна цінність (документи) буде в S3 та PostgreSQL.

## 7. Tandoor Recipes (`tandoor`)
- **База даних:** Спільна PostgreSQL (через CloudNativePG).
- **Навіщо диск:** `staticfiles` та `mediafiles`.
- **Готовність до відключення реплікації:** Майже готово
- **План робіт:**
  - БД PostgreSQL вже має HA.
  - Tandoor нативно підтримує AWS S3. Треба прописати S3 змінні (`S3_BUCKET_NAME`, `S3_REGION_NAME` тощо) для збереження `mediafiles` безпосередньо в OCI Object Storage.
  - PV для `staticfiles` можна замінити на `emptyDir`, налаштувавши команду ініціалізації на копіювання/компіляцію статики (`collectstatic`) під час старту поду, або також розмістити статику на S3.

## 8. VictoriaMetrics (`victoriametrics`)
- **База даних:** Власна Time-Series Database (TSDB).
- **Навіщо диск:** Збереження зібраних метрик.
- **Готовність до відключення реплікації:** Так
- **План робіт:**
  - Зняти реплікацію з Longhorn.
  - Якщо дім падає, метрики домашнього кластера і так недоступні для збору. Для локального OCI моніторингу можна запустити інший інстанс або налаштувати `vmagent` писати одночасно у дві незалежні БД (вдома і в хмарі), але реплікувати сам диск через WAN немає жодного сенсу.

## 9. Wishlist (`wishlist`)
- **База даних:** Вбудована SQLite.
- **Навіщо диск:** `/usr/src/app/data` (БД) та `/usr/src/app/uploads` (зображення).
- **Готовність до відключення реплікації:** Ні
- **План робіт:**
  - **БД:** Реплікувати SQLite за допомогою **Litestream** на OCI S3.
  - **Зображення:** Оскільки Wishlist не має нативної конфігурації для S3, необхідно змонтувати S3-бакет за допомогою S3 CSI (rclone mount/s3fs) у директорію `uploads`. Це дозволить зберігати картинки у хмарі прозоро для сервісу.
