# Список сервісів з Persistent Volumes (PV) та план відмови від георозподіленої реплікації Longhorn

Нижче наведено перелік усіх сервісів у кластері, які використовують персистентні томи (Persistent Volume Claims), разом з їхніми базами даних, призначенням дисків, а також планом міграції для відключення реплікації Longhorn на OCI (щоб сервіси залишались працездатними у хмарі при відключенні дому).

## 1. Actual Budget (`actualbudget`)
- **База даних:** Вбудована SQLite.
- **Навіщо диск:** Зберігання файлів внутрішньої бази даних та користувацької інформації про бюджети (монтується у `/data`).
- **Готовність до відключення реплікації:** Так (Готово)
- **План робіт:**
  - **БД:** Налаштовано **Litestream** для реплікації локальної SQLite-бази в OCI Object Storage.
  - **Файли:** Налаштовано rsync-sidecar (`backup-files`), який автоматично синхронізує завантажені чеки/вкладення у змонтований CSI S3 бакет.
  - Повністю позбулися використання Longhorn для цього сервісу, замінивши його на `emptyDir` + S3.

## 2. CloudNativePG (`cnpg`)
- **База даних:** Безпосередньо сам кластер бази даних PostgreSQL (`shared-db`).
- **Навіщо диск:** Збереження файлів бази даних PostgreSQL, таблиць, WAL логів (використовує клас `longhorn-postgres`).
- **Готовність до відключення реплікації:** Так (Готово)
- **План робіт:**
  - Томи переведено на StorageClass `longhorn-postgres`, який зберігає дані виключно на локальних нодах (`numberOfReplicas: 1`, `strict-local`).
  - Висока доступність (HA) в гібридній мережі забезпечується на рівні самої PostgreSQL (через асинхронну потокову реплікацію CloudNativePG).

## 3. ESPHome (`esphome`)
- **База даних:** Не використовує базу даних.
- **Навіщо диск:**
  - `/config`: Зберігання конфігураційних YAML файлів пристроїв.
  - `/config/.esphome`: Зберігання кешу для пришвидшення компіляції прошивок розумного дому.
- **Готовність до відключення реплікації:** Так (Готово)
- **План робіт:**
  - Сервіс наразі вимкнений (`replicas: 0`). Оскільки він компілює прошивки виключно для пристроїв домашньої мережі, за відсутності доступу до дому його робота в хмарі не має сенсу.

## 4. FreeLingo (`freelingo`)
- **База даних:** Спільна PostgreSQL (через CloudNativePG) та власний Redis (для кешу/брокера).
- **Навіщо диск:**
  - Бекенд (`backend`): Збереження згенерованих аватарів (`/app/avatars`) та аудіофайлів (`/data/audio`).
  - Redis (`redis`): Персистентне зберігання даних кешу (`/data`).
- **Готовність до відключення реплікації:** Так (Готово)
- **План робіт:**
  - **БД:** PostgreSQL вже реплікується через CNPG.
  - **Redis:** Переведено на `emptyDir` (для кешу/брокера).
  - **Файли:** Змонтовано єдиний S3-бакет (`freelingo-data-s3`) з підкаталогами `avatars` та `audio` замість класичних Longhorn PV.

## 5. LubeLogger (`lubelogger`)
- **База даних:** Вбудована SQLite (АЛЕ підтримує PostgreSQL).
- **Навіщо диск:**
  - `/App/data`: Збереження бази даних та фотографій чеків/деталей.
  - `/root/.aspnet/DataProtection-Keys`: Збереження ключів сесій ASP.NET.
- **Готовність до відключення реплікації:** Так (Готово)
- **План робіт:**
  - **База даних:** Базу успішно переведено на PostgreSQL у спільному кластері **CloudNativePG** (`shared-db`), де пароль генерується автоматично через IaaC (без ручних секретів).
  - **Фотографії та ключі ASP.NET:** S3-бакет (`lubelogger-files-s3`) змонтовано як PVC. Підкаталоги `data` та `keys` безпечно ізолюють файли застосунку та ключі захисту даних ASP.NET.
  - Повністю усунуто залежність від Longhorn PV. Старі диски `lubelogger-data` та `lubelogger-keys` більше не використовуються.

## 6. Paperless-ngx (`paperless`)
- **База даних:** Спільна PostgreSQL (через CloudNativePG) та локальний Redis.
- **Навіщо диск:** Папки `data`, `media`, `consume`, `export`.
- **Готовність до відключення реплікації:** Так (Готово)
- **План робіт:**
  - **БД:** PostgreSQL вже реплікується через CNPG.
  - **Файли:** Документи (`media`) перенесено в OCI Object Storage через `s3-rclone` PVC.
  - **Кеші/Індекси:** `consume`, `export` замінено на `emptyDir`. Диск `data` (з індексом) залишено на локальному `longhorn-postgres` для максимальної швидкості пошуку без мережевих затримок.

## 7. Tandoor Recipes (`tandoor`)
- **База даних:** Спільна PostgreSQL (через CloudNativePG).
- **Навіщо диск:** `staticfiles` та `mediafiles`.
- **Готовність до відключення реплікації:** Так (Готово)
- **План робіт:**
  - БД PostgreSQL успішно мігровано на `shared-db`.
  - Диск `mediafiles` (фото рецептів) перенесено на S3 Object Storage через `s3-rclone` PVC.
  - Диск `staticfiles` переведено на `emptyDir`, оскільки статика компілюється під час старту.
  - Усі класичні диски Longhorn відв'язані і можуть бути видалені.

## 8. VictoriaMetrics (`victoriametrics`)
- **База даних:** Власна Time-Series Database (TSDB).
- **Навіщо диск:** Збереження зібраних метрик.
- **Готовність до відключення реплікації:** Так (Готово)
- **План робіт:**
  - Знято реплікацію з Longhorn.
  - Диск переведено на StorageClass `longhorn-postgres`, який зберігає дані локально без мережевої реплікації (`numberOfReplicas: 1`). Стару історію метрик очищено.

## 9. Wishlist (`wishlist`)
- **База даних:** Вбудована SQLite.
- **Навіщо диск:** `/usr/src/app/data` (БД) та `/usr/src/app/uploads` (зображення).
- **Готовність до відключення реплікації:** Так (Готово)
- **План робіт:**
  - **БД:** Налаштовано реплікацію SQLite за допомогою **Litestream** на OCI S3.
  - **Зображення:** S3-бакет успішно змонтовано за допомогою S3 CSI (`s3-rclone`) у директорію `uploads`.
  - Залежність від Longhorn PV повністю усунуто.
